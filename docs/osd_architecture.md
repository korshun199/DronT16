# Архитектура OSD DronT16

Схема цифрового управления приёмник → Raspberry → полётник описана отдельно в
[`docs/crsf_bridge_architecture.md`](crsf_bridge_architecture.md).

## Назначение

DronT16 использует два независимых механизма экранных данных:

1. штатное OSD Betaflight, которое полётный контроллер MAX7456 уже накладывает
   на аналоговый `Video OUT`;
2. собственное OSD Raspberry Pi — рамка захвата, контур, крестик и линия к
   выбранной цели.

Raspberry Pi не считывает символы штатного OSD и не рисует их заново. Для неё
   штатное OSD является частью входного видеокадра.

## Полный видеотракт

```text
FC Video OUT
  │ аналоговый NTSC с OSD Betaflight
  ▼
EasyCap /dev/video0
  │ MJPG 720x480 @ 25 fps
  ▼
OpenCV VideoSource
  │ захват полного кадра без обрезки
  ▼
DronT16 overlay
  │ добавляет только собственные графические элементы
  ▼
DRM/KMS J7 Raspberry Pi
  │ композитный выход 720x480i
  ▼
штатный передатчик → очки пилота
```

В обычном режиме на J7 должен попадать тот же штатный OSD Betaflight, который
виден при прямом подключении монитора к Video OUT FC, плюс только наложение
DronT16. Штатные элементы не должны исчезать при изменении режима захвата.

## Согласование формата

Текущий EasyCap подтверждён аппаратно в формате:

```text
MJPG 720x480 @ 25 fps
```

В секции `[osd.output]` файла `config/dront16.toml` установлен единый стандарт:

```toml
[osd.output]
video_standard = "NTSC"
```

При NTSC J7 должен использовать режим `720x480i`. Нельзя выбирать первый
режим из списка DRM: Raspberry также предоставляет `704x432i`, `720x576i` и
другие режимы. Пересчёт 720x480 в другой размер может исказить или удалить
тонкие символы межстрочного OSD MAX7456.

Если размеры входа и J7 совпадают, `J7Output` не выполняет масштабирование
исходного кадра. Собственные элементы DronT16 рисуются после захвата поверх
этого кадра.

## Отдельный CRSF-тракт RSSI/LQ

Данные RSSI/LQ не идут через видеокабель. Они проходят отдельным цифровым
каналом CRSF:

```text
CRSF-приёмник TX
  │ Raspberry pin 10 / GPIO15 / /dev/ttyAMA0
  ▼
CRSF-мост Raspberry
  │ pin 8 / GPIO14 → UART1 RX полётника
  ▼
Betaflight
  │ штатное OSD получает RSSI/LQ из LINK_STATISTICS
  ▼
Video OUT FC → EasyCap → J7 → очки
```

Кадр `0x16` (`RC_CHANNELS_PACKED`) содержит стики и AUX. Кадр `0x14`
(`LINK_STATISTICS`) содержит RSSI, LQ и SNR. Мост должен пересылать оба типа
в режиме `LIVE`:

```text
LIVE:
  RC 0x16              → переслать в FC
  LINK_STATISTICS 0x14 → переслать в FC

TAKEOVER CH7:
  свежий RC 0x16       → подавить или заменить сохранённым кадром
  LINK_STATISTICS      → не использовать для подмены управления

DISARM CH5:
  немедленно передать RC-кадр DISARM
```

Если RC работает, но RSSI/LQ в Betaflight OSD отсутствуют, сначала проверяются
кадры `0x14` в журнале моста. Наличие `forwarded` само по себе доказывает
только прохождение RC и не подтверждает прохождение link-statistics.

## Диагностические признаки

Нормальный журнал моста содержит:

```text
[RPI] STATUS: link=OK ... link_stats=...
[RPI] CRSF LINK_STATS forwarded: RSSI=... LQ=... SNR=...
```

Интерпретация:

- есть RC, но нет `LINK_STATS` — приёмник не выдаёт кадры `0x14` или они не
  дошли до Raspberry;
- есть `LINK_STATS`, но RSSI/LQ не появляются на FC — проверяется линия
  Raspberry TX → FC UART1 RX и настройки CRSF/Betaflight;
- штатное OSD есть напрямую с FC, но пропадает на J7 — проверяется формат
  EasyCap, режим J7 и сохранение полного кадра до наложения DronT16;
- пропало всё изображение — проверяется DRM/J7 и не запускается ли второй
  процесс захвата камеры.

## Границы ответственности

- Betaflight формирует штатное OSD и рассчитывает отображаемые RSSI/LQ.
- EasyCap только оцифровывает аналоговый кадр.
- OpenCV не интерпретирует штатные символы OSD.
- DronT16 добавляет только собственную графику.
- CRSF-мост передаёт управление и служебные link-statistics.
- J7 выдаёт итоговый кадр в сторону штатного видеопередатчика.
