# Архитектура CRSF-моста DronT16

## Назначение моста

CRSF-мост — это программный посредник между радиоприёмником и полётным
контроллером. Raspberry Pi не является самостоятельным радиоприёмником и не
заменяет передатчик. Она принимает кадры CRSF от приёмника, анализирует их,
при необходимости изменяет только разрешённые кадры и передаёт результат в
Betaflight.

Мост нужен для трёх задач:

1. прозрачная передача обычных команд пилота;
2. чтение положения CH5/CH6/CH7 и других AUX на Raspberry;
3. безопасный перехват управления при стендовом или рабочем сценарии
   filesafe.

## Физическая схема

```text
Radiomaster TX12
        │ радиоканал
        ▼
CRSF-приёмник
        │ TX
        ▼
Raspberry Pi pin 10
GPIO15 / RXD0 / /dev/ttyAMA0
        │
        │ CRSF 420000 бод
        ▼
scripts/crsf_bridge.py
        │ TX
        ▼
Raspberry Pi pin 8
GPIO14 / TXD0 / /dev/ttyAMA0
        │
        ▼
Betaflight UART1 RX
FC resource SERIAL_RX 1 = PB7
```

Общая земля Raspberry, приёмника и полётного контроллера обязательна. Уровни
сигналов и распиновка должны быть подтверждены до подключения питания.

Рабочий CRSF-порт Raspberry — `/dev/ttyAMA0`. Симлинк `/dev/serial0` на этой
плате указывает на другой UART и для физического CRSF GPIO14/15 не применяется.

## Как проходит обычная команда

Пульт кодирует положение стиков и тумблеров в CRSF-кадр. Приёмник передаёт
кадр по UART Raspberry. Мост проверяет длину и CRC8, затем разбирает 16 каналов.
В состоянии `LIVE` RC-кадр передаётся в UART полётника с теми же каналами.

```text
Пилот двигает стик
  ↓
TX12 формирует CRSF
  ↓
приёмник выдаёт кадр
  ↓
Raspberry проверяет CRC и читает CH1...CH16
  ↓
Raspberry пересылает кадр в Betaflight
  ↓
Betaflight использует roll/pitch/throttle/yaw/AUX
  ↓
FC управляет ESC и моторами
```

В обычном режиме Raspberry не меняет каналы. Поэтому задержка моста состоит
только из чтения UART, проверки кадра и записи его в UART полётника.

## Типы CRSF-кадров

### `0x16` — RC_CHANNELS_PACKED

Основной кадр управления. Содержит 16 каналов CRSF:

- CH1–CH4 — стики;
- CH5 — ARM/DISARM;
- CH6 — режимы DronT16 по принятой настройке;
- CH7 — программная имитация потери связи;
- остальные каналы — AUX и дополнительные функции.

Именно этот кадр Raspberry использует для принятия решений о режимах.

### `0x14` — LINK_STATISTICS

Служебный кадр радиолинии. Содержит RSSI, LQ, SNR и сопутствующие параметры
канала. Он нужен полётному контроллеру для расчёта состояния RX и отображения
RSSI/LQ в штатном OSD Betaflight.

В режиме `LIVE` мост пересылает `0x14` без изменения. Передача только `0x16`
означает, что управление стиками будет работать, но RSSI/LQ в полётнике может
пропасть.

## Приоритеты обработки

Приоритеты фиксированы:

```text
1. DISARM CH5
2. аварийная обработка filesafe / посадочного контроллера
3. TAKEOVER CH7
4. обычная передача LIVE
```

### `LIVE`

```text
RC 0x16              → разобрать → переслать в FC без изменения
LINK_STATISTICS 0x14 → переслать в FC без изменения
```

Raspberry параллельно пишет в журнал каналы пилота, состояние моста и данные
MSP от FC.

### `TAKEOVER`

При активном CH7 и подтверждённом ARM Raspberry сохраняет последний полный
корректный RC-кадр. Новые RC-команды пилота к FC не проходят. Вместо них мост
передаёт сохранённый или изменённый посадочным контроллером кадр.

```text
новый RC 0x16 от пилота → подавить
сохранённый RC 0x16     → повторить/изменить → FC
```

Положение CH7 и CH5 продолжает приниматься с приёмника. Служебные кадры не
должны превращаться в RC-команды и не должны сбивать механизм повтора.

### Возврат в `LIVE`

После возврата CH7 в нормальное положение следующий корректный живой RC-кадр
снова передаётся в FC. Raspberry прекращает подмену каналов.

### `DISARM`

CH5 имеет высший приоритет в любом состоянии. При DISARM Raspberry немедленно
формирует корректный RC-кадр с безопасным значением CH5, пересчитывает CRC8 и
передаёт его в FC. Затем управление возвращается живому каналу приёмника.

## Что делает Betaflight

Raspberry не формирует PWM и не управляет моторами напрямую. Она передаёт
Betaflight RC/setpoint-кадры. Полётный контроллер сам выполняет:

- декодирование RC;
- ARM/DISARM;
- стабилизацию;
- PID-регуляторы;
- расчёт выходов ESC;
- формирование штатного OSD;
- расчёт RXLOSS/RSSI/LQ по доступным данным CRSF.

Посадочный контроллер Raspberry может изменять RC-значения газа, крена,
тангажа и рыскания, но окончательное управление моторами остаётся внутри
Betaflight.

## MSP — отдельный канал датчиков

CRSF-мост и MSP-канал не являются одним протоколом:

```text
Raspberry GPIO0/1, pin 27/28
UART /dev/ttyAMA1
        ⇄
FC UART2 MSP
```

По MSP Raspberry получает высоту, вариометр, крен, тангаж, yaw и сырые данные
магнитометра. Эти данные используются для журналирования и посадочного
контроллера. MSP не заменяет CRSF RC-мост.

## Видеотракт — отдельный от CRSF

Команды и видео идут разными путями:

```text
CRSF: приёмник → Raspberry → FC UART1

Видео: FC Video OUT с OSD
      → EasyCap
      → OpenCV
      → добавление рамки DronT16
      → J7
      → штатный передатчик → очки
```

CRSF-мост не передаёт видеокадры. Видеомодуль не передаёт стики. Штатное OSD
Betaflight уже находится в аналоговом видеокадре до EasyCap; DronT16 добавляет
собственную графику поверх него.

## Журнал и диагностика

Все сообщения моста пишутся в `simulator_filesafe.log` с меткой сущности:

```text
[PILOT] RC и AUX, полученные от приёмника
[RPI] решения, состояния моста и команды в FC
[FC] датчики и состояния, полученные по MSP
```

Признаки исправной работы:

```text
[RPI] STATUS: link=OK state=LIVE received=... forwarded=...
[RPI] CRSF LINK_STATS forwarded: RSSI=... LQ=... SNR=...
[PILOT] RC snapshot: CH1=... CH5=... CH7=...
```

`forwarded` подтверждает передачу кадров в FC, но для подтверждения RSSI/LQ
нужна отдельная строка `CRSF LINK_STATS forwarded`. Если `received=0`, мост не
получает CRSF с приёмника и проверять фильтр кадров бессмысленно.

## Краткая памятка

```text
UART0 / ttyAMA0 / pin 10 ← CRSF RX от приёмника
UART0 / ttyAMA0 / pin 8  → CRSF TX к FC UART1 RX
UART1 / ttyAMA1 / pin 27 → MSP TX к FC UART2 RX
UART1 / ttyAMA1 / pin 28 ← MSP RX от FC UART2 TX

0x16 = управление RC
0x14 = RSSI/LQ/SNR
CH5   = высший приоритет DISARM
CH7   = программный TAKEOVER/LINK_LOST
```
