# DronT16 — единая техническая документация

## 1. Назначение и границы

DronT16 — бортовая система Raspberry Pi 5 для обработки собственной
фронтальной камеры, отображения собственного OSD и выполнения явно разрешённых
задач по данным полётного контроллера.

Пилот сам выбирает область и объект. Система не распознаёт класс объекта, не
ищет похожую цель после потери и не переключается на новую цель без команды
«Захватить».

Текущая платформа:

- полётный контроллер HAKRCF405V2 на Betaflight;
- приёмник Cyclone 2.4 GHz Nano по CRSF;
- передатчик Radiomaster TX12;
- Raspberry Pi 5 как вычислительный арбитр;
- фронтальная камера Raspberry Pi;
- датчики FC: гироскоп, акселерометр, барометр, магнитометр/компас и GPS.

Raspberry не формирует PWM моторов. Быстрая стабилизация, PID, ARM/DISARM и
выходы ESC остаются внутри Betaflight. Команды Raspberry проходят как RC или
setpoint через проверенный мост.

На ветке `v4_simulator_gps` разработка ведётся локально на ноутбуке. Изменения
не загружаются на Raspberry без отдельного разрешения.

## 2. Роли компонентов

```text
PILOT  → TX12 → CRSF-приёмник → RPI
RPI    → анализирует команды, видео и датчики; принимает решения по задаче
FC     → датчики, стабилизация, PID, OSD Betaflight и моторы
RPI    → ограниченные RC/setpoint-команды → FC
```

Обозначения журнала:

- `PILOT` — команда или положение канала от пульта/приёмника;
- `RPI` — решение, состояние, ограничение или команда Raspberry;
- `FC` — показание или состояние полётного контроллера.

## 3. Видеорежимы

```text
DIRECT  →  CAPTURE  →  FOLLOW
   ↑          ↓          ↓
   └────────── Отбой ─────┘
```

1. `DIRECT` — собственная камера Raspberry идёт напрямую на J7.
2. `CAPTURE` — по команде пилота фиксируется выбранная область, добавляются
   рамка и линия направления, обработанный кадр выдаётся на J7.
3. `FOLLOW` — сопровождается только ранее захваченная цель; расчёт направления
   может формировать ограниченные команды FC после отдельного разрешения.
4. Потеря цели не выбирает новую цель. Для продолжения нужна новая команда
   `CAPTURE`.
5. `Отбой` возвращает `DIRECT`.

В ноутбучной модели клавиши `1..4` и веб-команды — только тестовый источник.
На Raspberry источник команд заменяется CRSF-каналами; верхняя логика режимов
остаётся общей.

## 4. CRSF-мост

### Физическая схема

```text
TX12 ──радиоканал──> CRSF-приёмник TX
                         │
                         └─> Raspberry pin 10 / GPIO15 / RXD0 / /dev/ttyAMA0

Raspberry pin 8 / GPIO14 / TXD0 / /dev/ttyAMA0
                         └─> FC UART1 RX / SERIAL_RX 1 = PB7
```

Общая земля Raspberry, приёмника и FC обязательна. Уровни и распиновка
проверяются до подключения питания. Для CRSF используется `/dev/ttyAMA0`,
`420000` бод; `/dev/serial0` для этой физической линии не считать заменой без
проверки.

### Поток кадров

- `0x16 RC_CHANNELS_PACKED` — 16 RC-каналов;
- `0x14 LINK_STATISTICS` — RSSI, LQ, SNR и параметры радиолинии.

В `LIVE` мост проверяет длину и CRC8 и передаёт оба типа кадров без изменения.
В `TAKEOVER` свежие RC-кадры подавляются или заменяются удерживающим кадром;
служебные `LINK_STATISTICS` не превращаются в команды управления.

Приоритет:

```text
DISARM CH5 → failsafe/удержание RPI → TAKEOVER CH7 → LIVE
```

Для текущей настройки:

- `CH5 >= 1700` — ARM, `CH5 <= 700` — DISARM;
- `CH7 >= 1700` — стендовая имитация потери связи, `CH7 <= 700` — LINK_OK;
- при DISARM Raspberry формирует корректный кадр с безопасным CH5 и немедленно
  возвращает живое управление.

При реальной потере радиокадров RPI не может получать команды пилота. Поэтому
Betaflight обязан иметь собственный настроенный failsafe на случай отказа RPI.

### Журнал моста

```text
[PILOT] RC и AUX от приёмника
[RPI]   LIVE/TAKEOVER, подавление и передача кадров, решения
[FC]    MSP-датчики и состояния полётника
```

Наличие `forwarded` подтверждает прохождение RC, но не RSSI/LQ. Для штатного
OSD нужна отдельная строка пересылки `LINK_STATISTICS`.

## 5. MSP-канал датчиков

CRSF и MSP — разные каналы.

```text
Raspberry pin 27 / GPIO0 / UART1 TX → FC UART2 RX / PA3
Raspberry pin 28 / GPIO1 / UART1 RX ← FC UART2 TX / PA2
Raspberry pin 30 / GND              ↔ FC GND

Raspberry: /dev/ttyAMA1, 115200 бод
```

Текущий read-only парсер запрашивает:

- `MSP_ATTITUDE` — крен, тангаж, yaw;
- `MSP_ALTITUDE` — высота и вариометр;
- `MSP_RAW_IMU` — ACC/GYRO и сырые X/Y/Z магнитометра;
- `MSP_RAW_GPS` — fix, спутники, координаты, высота, скорость, курс, HDOP.

GPS запрашивается при `msp.gps_enabled = true`. GPS считается пригодным только
при fix и минимум четырёх спутниках. Сырые магнитные X/Y дают диагностический
курс `atan2(Y, X)` и пока не подменяют откалиброванный курс Betaflight.

Единицы `MSP_RAW_GPS` в парсере:

- latitude/longitude — `1e-7` градуса;
- altitude — метры;
- speed — `cm/s`, преобразуется в `m/s`;
- course — `0.1` градуса;
- HDOP — необязательное значение в `0.01`.

Устаревшие или неполные данные не являются основанием для опасной команды.

## 6. Удержание при потере связи

Автоматической посадки в актуальной схеме нет. Состояния:

```text
LIVE → LEVELING → TURNING → HOLDING
             └──────────────→ FAULT
DISARM — высший приоритет из любого состояния
```

После CH7 при подтверждённом ARM Raspberry:

1. фиксирует последние корректные RC-команды и высоту по барометру;
2. подавляет свежие команды пилота, но продолжает слушать CH7 и CH5;
3. выравнивает крен и тангаж;
4. удерживает высоту по барометру и вариометру;
5. выполняет разворот на `180°` по фактическому yaw, без фиксированного
   тайм-аута;
6. после разворота продолжает удерживать высоту и горизонт;
7. при LINK_OK возвращает живое управление;
8. при DISARM немедленно отправляет DISARM и прекращает автономные команды.

При пропаже свежего MSP-контракта действует `fault_action`; это не считается
успешным удержанием. GPS не используется как единственный источник высоты или
стабилизации, а камера не заменяет IMU-контур FC.

## 7. OSD и видеотракт

Штатное OSD Betaflight уже находится в аналоговом `Video OUT` FC. Raspberry не
считывает его символы и не рисует штатные элементы заново.

```text
FC Video OUT с OSD
  → EasyCap / OpenCV
  → собственное OSD DronT16
  → J7 Raspberry
  → штатный видеопередатчик
  → очки пилота
```

Текущий подтверждённый вход EasyCap — `MJPG 720x480 @ 25 fps`; рабочий стандарт
`NTSC`, J7 — `720x480i`. Нельзя автоматически выбирать другой режим DRM:
масштабирование может исказить или удалить межстрочные символы штатного OSD.

На ноутбуке общий кадр выводится через веб-морду на HDMI-монитор. На Raspberry
рабочий выход — J7, веб-морда остаётся диагностической.

## 8. Конфигурация и запуск

Главный конфиг — `config/dront16.toml`, формат TOML; параметры сопровождаются
русскими комментариями.

```bash
./run
```

Локальный безопасный тест привязки датчиков:

```bash
./run sensor-test
```

`sensor-test` использует настоящий `MspParser`, но синтетические MSPv1-кадры.
Он не открывает UART, камеру, CRSF-мост и не отправляет команды FC. Проверяет
CRC, дробленый поток, единицы, GPS fix/свежесть, магнитные оси и наличие
фронтальной камеры в карте источников.

Подробный журнал теста: `runs/sensor_binding_test.log`. Каталог `runs/` не
публикуется в Git.

## 9. Калибровка магнитометра

Зафиксированный стендовый результат от 19.09.2026:

- FC HAKRCF405V2, Betaflight 4.5.5;
- QMC5883, I2C device 1;
- ориентация платы: X вперёд, Y влево, Z вверх;
- `align_mag = DEFAULT`, склонение `0`;
- проверка выполнялась только на чтение по `/dev/ttyAMA1`, 115200 бод;
- два корректных оборота дали примерно `+359°` и `+360°`.

Временный CH8-тест и его автозапуск удалены. В рабочем коде остаются MSP yaw и
сырые магнитные оси; контроль `FAULT` и свежести MSP обязателен.

## 10. Безопасность и порядок испытаний

- до аппаратного теста команды управления проверяются без пропеллеров;
- прошивка, boot-параметры, сетевые настройки и питание платы не меняются
  автоматически;
- ручной DISARM имеет безусловный приоритет;
- при неизвестном состоянии новая цель и автопилот не запускаются;
- `security/` — коммерческий каталог и не входит в Git;
- `security_sample/` — только старый образец, не подключается автоматически;
- файлы, ключи, токены, device-specific дампы и логи не публикуются.

Порядок аппаратной проверки: сначала только чтение MSP и журнал, затем стенд
без винтов, затем неподвижная проверка наклона/курса/высоты/GPS. Управляющие
поправки разрешаются только после разбора журнала и отдельного согласования.
